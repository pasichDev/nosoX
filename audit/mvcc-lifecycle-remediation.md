# Managed MVCC lifecycle remediation

Local implementation and verification record, 2026-10-26; this is not an independent security audit.

`BadgerStore` now registers every committed read transaction under `readersMu`, atomically with loading the active fence. All public read helpers use `view`; mutation validation also registers its snapshot. The release path discards the transaction **before** unregistering it. Publishing does not wait for readers, so a mutation can publish while an older public view remains open without a read/write barrier deadlock.

The managed discard cutoff is the minimum of the complete active fence and all registered reader timestamps. It advances automatically after successful publication, reader release, and completed startup recovery. `NumVersionsToKeep` is explicitly one. This permits normal Badger compaction to discard obsolete committed versions while preserving the newest version at or below the oldest reader. An interrupted stage is newer than the active fence; its values and deletion tombstones remain above the cutoff. Startup scans those versions and recovers dirty keys before enabling discard. Before staging **any** subsequent candidate, the writer restores every dirty key from the complete snapshot and publishes this unchanged canonical state with its own fence. If restoration fails, the writer returns without touching a new candidate key. This bounds the dirty key set to one failed stage rather than the union of arbitrarily many different failed candidates. Only after restoration succeeds does the writer stage and publish the candidate. Successful publication clears dirty metadata and advances the cutoff. Failed staging never advances the complete fence.

Primary evidence is the pinned dependency `github.com/dgraph-io/badger/v4@v4.9.1`: `managed_db.go` documents `SetDiscardTs`; `levels.go` counts versions only at or below the cutoff and retains one such live version; `iterator.go` supplies all-version tombstones and exclusive `SinceTs`; `value.go` rewrites a value-log entry only when the LSM still references that exact version. Source links: [managed timestamps](https://github.com/dgraph-io/badger/blob/v4.9.1/managed_db.go), [compaction](https://github.com/dgraph-io/badger/blob/v4.9.1/levels.go), [value-log rewrite](https://github.com/dgraph-io/badger/blob/v4.9.1/value.go), [GC API](https://github.com/dgraph-io/badger/blob/v4.9.1/db.go). These pinned sources were inspected locally.

`Reclaim(ctx)` performs at most one `RunValueLogGC(0.5)` attempt, treating `ErrNoRewrite` as successful maintenance. It rejects concurrent attempts; a maintenance mutex serializes it with `Close`. Call it periodically during store lifetime, after writers have published new state; it does not acquire the writer or chain mutex. LSM compaction runs automatically. Badger provides no context-aware interruption for an in-flight GC: cancellation is checked before entering the call and again on return. This bounds the number of attempts, not wall-clock I/O latency. No per-call goroutine can outlive the returned call. Ordinary store use must stop before `Close`, as with the existing Store lifecycle.

`badger_mvcc_lifecycle_test.go` covers old/middle/current snapshots across overwrite/delete/recreation and reclamation; a public `view` held across a concurrent publish; failed partial/pre-fence stages, both in-process and after reopen, followed by reclaim, compaction and a different retry; context cancellation, overlapping maintenance and closed-store rejection. The physical compaction fixture disables automatic compactors, flushes four generations into separate tables using close/reopen, holds the old reader across a newer publication and explicit `Flatten`, verifies both required versions survive, releases the reader and flushes/compacts again, then checks that only the current value remains and all versions of a deleted key disappear. It asserts actual version removal, without relying on elapsed sleeps or disk byte ratios.

Repeated-failure coverage attempts twelve different candidate keys while restoration itself fails, then another twelve different candidates with restoration succeeding but candidate publication failing. The dirty key count remains one, including after reopen. No failed candidate becomes logically visible.

Startup recovery now records at most `MaxRecoveryKeys = 65,536` distinct unpublished keys. This exceeds both the native v4 suffix envelope (fewer than `44 × 1,024 + 1` touched keys) and trusted genesis (`3 × 10,000 + 4`). It fails closed with `ErrResourceBudget` before copying an excess key; it neither publishes nor deletes the pending state. The all-versions iterator retains tombstones, disables value prefetch, and seeks to `key || 0` after recording the newest future version of a user key. Badger's forward seek uses the first key at or after its argument, so this skips older versions of that exact user key while preserving zero-byte extension keys. Tests cover exact-limit/+1 rejection with a small private helper limit, repeated future versions, a latest tombstone, embedded-zero extension keys, reopen and a different successful retry.

Recovery metadata and repeated-version traversal are bounded; physical disk growth under persistent staging/restoration faults is not. Versions above the complete fence remain protected until restoration can publish successfully. A trusted whole-chain `ReplaceChain` import touching more than 65,536 keys is outside the native consensus suffix envelope: if interrupted, it may require explicit offline recovery rather than ordinary startup. Pre-v4 abandoned data can similarly exceed the recovery cap; explicit reset/import remains the upgrade policy, not silently dropping keys.

## Streaming startup verification

Persistent Badger startup replay now uses a temporary disk-backed `BadgerStore`, not a complete `memStore` and `stateEntries` map. One pinned source snapshot supplies genesis, tip and each canonical block. Each native block passes the same `Chain.validate` rules and ordinary `WriteBlock` transition before the next is read. The scratch database configures 32 MiB block cache, 16 MiB index cache, 8 MiB memtables with two memtables, and disabled synchronous durability (scratch is disposable). The final comparison walks pinned, ordered source/scratch iterators with value prefetch disabled and compares one logical record pair at a time using the existing semantic gob comparison. It ignores only the timestamp fence. Encoded block/state size checks precede potentially large source decoding.

This removes history-sized Go block collections and derived-state maps from the persistent replay path. It does not promise an exact process RSS ceiling: storage-engine table/file metadata, compaction workers, mapped files and Go runtime overhead remain in addition to the configured caches and per-record working set. Startup still performs O(history) verification work and needs additional O(history) scratch disk space beside the database; disk exhaustion fails verification rather than replacing trusted state. Scratch close and removal run on every return path, including invalid history or state mismatch. The memory backend intentionally remains an in-memory backend.

Streaming replay tests accept a valid four-block chain, reject missing/extra/corrupt state, changed block authorization and oversized block records, pin trusted genesis, and check scratch removal after successful and failed verification. Manual source inspection checks that replay retains no complete block collection or derived-state map; no flaky heap byte ratios stand in for this invariant. Existing pre-v4 databases require the documented explicit reset/import policy.

Existing abrupt-process-exit tests remain intact and exercise partial stage, prepublication fence and published-state reopen behavior. The lifecycle suite exercises the GC API but does not force a value-log-file rewrite; the physical reclamation proof concerns obsolete LSM versions. Value-log reclamation remains subject to Badger's eligible-file sampling and compaction statistics, and accepted historical blocks/undo data remain live storage rather than reclaimable garbage. Long-lived readers intentionally delay removal of versions they may still read; abandoned unpublished stages remain until a successful publication restores them. This is a safety requirement, not a guarantee of constant disk use.
